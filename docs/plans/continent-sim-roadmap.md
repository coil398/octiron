## ⏭️ ワークフロー後の作業計画

### 1. 🔍 可読性・因果可視化 (§8) ── 最優先

> 設計書いわく「可読性が最大の壁。プレイヤーが選べない以上、創発した意思決定の理由を可視化できないと技術ツリーも政体もパークもノイズに見える」。

- **「なぜ」パネル**: 国家を選ぶと「なぜ軍国化したか」「なぜこの技術を先に取ったか」を状態 + ログで提示。
- **年代記の物語性強化**: 単発イベントの羅列でなく、因果の連鎖（3 度の氾濫 → 灌漑発明 → 河川大都市）を 1 エントリに束ねる。
- **オーバーレイ拡充**: 国境・交易路・技術水準・災害リスクのヒートマップ切替。

### 2. ⚖️ バランス調整

- どの地形にも旨味と弱点を持たせ、特定地形が常に最適解にならないようにする（地図を描く意味の担保）。
- 災害頻度・K 書き換え量・成長率・戦争係数のチューニング。回しながら数値を詰める。

### 3. 🖱️ エディタ / 介入の作り込み

- 介入リソース（信仰ポイント）の経済設計（回復源 = 人口・崇拝、クールダウン）。
- ブラシ UX（地形種・標高・資源・河川描画）、アンドゥ、プレビュー。
- カメラのパン + **ズーム**（エンジン要拡張: 現状パンのみ）。

### 4. 🎨 アート拡張

| 項目 | 必要なもの |
|---|---|
| 海岸遷移タイル / バイオーム変種 | `/game-art` で追加生成 → 再パック |
| キャラ / ユニットのスプライト（ユニット視点を作る段で） | Codex 生成 + deai `--remove-bg`（透過） |
| アニメーション | **エンジンにアニメヘルパー追加**（スプライトシート + フレーム送り。未実装） |

### 5. ⚙️ エンジンの残課題

| 穴 | 用途 |
|---|---|
| カメラズーム / スクリーン↔ワールド変換の本格化 | マップ操作・大マップ |
| タイルマップ一括描画の最適化 | グリッドを大きくしたときの負荷（現状は全タイル毎フレーム描画） |
| スプライトアニメーション | キャラのアニメ |

### 6. 🌐 オンライン (§10) ── 単機が固まった後

- **非同期マッチ**を主に据える: 各自が開始地域（地形＋資源＋初期シード＋パーク）を仕込んで提出 → サーバが N 年シミュレート → 領土・人口・技術・戦争結果で勝敗。発展シミュの低速さと構造的に噛み合う。少人数開発の射程内。
- リアルタイム神 vs 神 / 協力建設は後段（ネットコード負荷大）。

### 7. 🎛️ プリセット

- **シナリオ/マッププリセット**: 「Pangaea」「Archipelago（島嶼）」「Highlands」「Desert World」「Ice Age」等を、生成シード＋パラメータ（海面・気候帯・大陸数・資源密度）のプリセットとして用意。lib.rs の小機能（build-out 後）。
- **アートスタイルプリセット**: `/game-art` の art-bible / palette を差し替え可能にし、別テイスト（淡色／高彩度／モノクロ等）のタイルセットを切替生成できるようにする。

### 8. 🧱 アセットライブラリ拡張（現在 9 枚 → 大量化）

> 状況変化に応じてマップタイルが細かく変わるには、**状態変種タイル**が要る。キャラ・動物・特殊タイルも大量に必要。`continent-asset-library` ワークフローで一括生成中。

| 種別 | 例 |
|---|---|
| 地形の状態変種 | plains→farmland/irrigated/scorched, forest→dense/burnt, mountain→snowcapped/volcanic, ocean→stormy, desert→oasis |
| 遷移タイル | 海岸線・河川の曲がり |
| 特殊タイル | volcano, ruins, capital-city, town, village, fortress, trade-port, road, farmland |
| キャラ（透過） | tribesperson, farmer, soldier, archer, sailor, noble, nomad, priest, merchant, monarch |
| 動物（透過） | deer, boar, horse, cattle, wolf, bird, fish, whale |

状態変種を実際に画面で出すには、sim が状態（被災・灌漑・発展度）を持ち、描画がタイルを差し替える配線が要る（build-out 後の統合作業）。

## ⚠️ 設計上のトレードオフ（常に意識）

- 工数の重心は地図描画 UI でなく **発展ルール・災害判定・文明 AI の因果モデル**側。
- システムを足すたびに「なぜ」の可視化 (§8) が必要になる ── 機能追加と可読性は掛け算。
- 4X システムを丸ごと借りると AI 駆動 × 可読性の負荷が掛け算で増える。**§1 の因果ループに効くものから薄く入れて回す**。
